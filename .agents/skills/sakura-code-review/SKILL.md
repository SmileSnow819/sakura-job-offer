# Sakura Code Review

目标是发现影响用户、数据、需求或长期维护的具体问题。默认只读；除非用户明确要求，不修改代码、不提交、不推送。

采用 [Google Engineering Practices](https://google.github.io/eng-practices/review/reviewer/) 的正确性与可维护性优先原则，并借鉴 [Conventional Comments](https://conventionalcomments.org/) 区分阻塞问题、建议、疑问和细节。项目风险与本输出契约优先。

## 确定范围

1. 明确基线与目标：工作区 diff、两个 commit、分支或 PR。范围不明时用 Git 事实缩小，不把整个仓库塞进本次 CR。
2. 阅读需求、设计或验收条件；没有书面需求时，明确只按现有行为和改动意图审查。
3. 查看完整 diff、调用上下文和相关测试。未打开实际代码前不下结论。
4. 区分本次改动、用户未提交内容与既有历史债务。

## 审查顺序

1. **需求与范围**：遗漏验收条件，或混入未授权功能、重构和数据变更。
2. **正确性与数据安全**：状态转换、标识匹配、失败路径、跨标签页、localStorage 损坏和数据丢失。
3. **隐私与安全**：备注默认保护，HTML/CSV 转义，外部 URL 和未知数据校验。
4. **交互与可访问性**：键盘、焦点、弹窗关闭、窄屏、空状态、长文本、加载和错误反馈。
5. **测试与验证**：测试是否覆盖真正可能失败的行为；构建或单测不能冒充视觉和导出验收。
6. **可维护性**：职责、重复、类型、命名、JSDoc、样式边界及开发规范的硬性规则。

## 严重等级

- **P0 阻断**：广泛或不可恢复的数据破坏、严重安全/隐私事故，或主流程完全不可用。
- **P1 高**：常见条件下功能错误、数据丢失、明显需求违背或关键回归；合入前必须修复。
- **P2 中**：特定条件下的真实错误、重要交互/可访问性遗漏，或显著增加后续出错概率的设计问题。
- **P3 低**：低影响但有证据的可维护性问题。个人偏好、自动格式问题和未触及的历史债务不作为 finding。

等级按“影响 × 发生可能性”判断，不按修复工作量判断。拿不准是否为真实缺陷时标为 `question`，不虚构 P 级问题。

## Finding 证据契约

每个 finding 必须包含：

```text
[P1] 标题说明可观察到的失败
位置：文件和最小行范围
触发：什么输入、状态或操作会进入问题路径
影响：用户、数据或系统会发生什么
依据：代码路径、需求或可复现证据
建议：最小修复方向；不要求替作者重写整段代码
```

标题不能写“建议优化”“代码不够优雅”。行号只定位引入问题的最小范围；跨文件问题以根因位置为主。

以下内容不能作为 finding：

- 没有触发路径的猜测；
- 与本次 diff 无关的旧问题；
- 仅因写法不同于审查者偏好；
- 已由类型、测试或上下文明确排除的风险；
- 要求没有实际调用方的“更完整”功能。

非阻塞意见使用 Conventional Comments 风格：`suggestion:` 给可选改进，`question:` 请求上下文，`nitpick:` 表示极小风格意见。不得伪装成 P0–P3 finding。

## 输出格式

先列 findings，按 P0 到 P3 排序；随后只在需要时列出“待确认问题”“验证缺口”和一句话结论。

没有 finding 时明确写“未发现可证实的问题”，并列出验证缺口。不要用优点总结稀释缺陷，也不要为了显得认真凑数。审查结果不等于已修复或已验证。
