# 清理推理过程残留

所谓残留，是文字站在“写这段代码的人当时怎么想”的视角，而不是站在当前仓库和未来维护者的视角：它引用未提交草稿、叙述 PR / review，逐步讲解控制流，或留下没有落点的计划。处理方式不是盲删；先提取仍然真实的事实，用当前状态重写，再删除过程叙述。

## 一个判断问题

对每段可疑文字问：一个只拿到当前仓库、没有 PR 讨论、聊天记录和未提交草稿的读者，能否解析每个引用并验证每项主张？

不能，就重写存活事实或删除。能，也不代表它适合留在 README、JSDoc 或注释：这些当前状态文档通常不需要变更故事。

## 常见类型

1. **失效的会话引用**：`decision 7`、`audit C2`、草稿章节号、阶段代号、内部“设计账本”。改为链接到已提交的决定文件，或删除引用后直接陈述事实。
2. **PR / 堆栈视角**：`这个 PR`、`后续 PR`、`上一个 commit`、`review 中被拒绝`。改为当前机制、限制或明确 TODO。
3. **变更叙述**：`以前`、`不再`、`这次改动`、`当前版本`。改写为现在的行为；回归原因可写成“缺少 X 时会发生 Y”。
4. **对 reviewer 的辩护**：`这个 cast 是安全的，因为……`。改为代码真正依赖的不变量，或删除注释。
5. **控制流和测试解说**：`先做 A，再做 B`、逐步解释显而易见分支、描述测试如何运行。删除；只保留不直觉的约束或结果。
6. **无落点的计划残渣**：`现在应该够了`、`以后可能处理`、`暂时没问题`。改为实际限制，或转成有 owner 的 TODO / issue。
7. **语言污染**：目标文档语言中残留另一种工作语言、私有分隔符或未翻译草稿短语。翻译或删除。

## 不应误删的内容

保留当前仍可验证、且对维护有用的内容：

- 已解析的 issue、外部标准、公开设计文档和正式 TODO 引用。
- 解释 lint disable、空 catch、覆盖率排除等例外的真实理由。
- 表达当前风险的反事实：例如“没有 X 时会发生 Y”。
- 运行时旧/新资源交接等真正的生命周期语义。
- 可复核的测量、上限、兼容承诺、安全约束和重审条件。
- Agent Note 中为了说明选择而保留的 Alternatives considered；但它们也应描述可验证的方案与取舍，而不是会议实录。

## 工作流

1. 明确范围；不要修改 vendored 第三方代码、生成文件或冻结归档，除非用户明确要求。
2. 先只读审查。搜索常见模式，但把搜索结果当成候选，逐段判断语义。
3. 删除前列出该段携带的事实：义务、限制、因果关系、可验证引用和失败条件。重写后逐项确认没有丢失或反转。
4. 从事实 owner 开始修改：生成文档改源文档或生成器，配对文档同步更新，用户可见文案结合实际行为确认。
5. 重读修改后的完整段落，确认它描述的是当前状态而非这次编辑本身；再运行与改动范围匹配的文档或代码检查。
