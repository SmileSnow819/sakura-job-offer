# Sakura 前端开发规范

目标是让新增代码可读、可验证且不破坏投递数据。先阅读相邻模块并复用现有组件、Hooks、工具函数、类型和样式；规范不授权清理任务范围外的历史代码。

## 规则等级

- **必须**：新增或修改的代码不满足时，应在交付前修正；确有例外时说明具体原因和风险。
- **重构信号**：需要主动评估，但不能只凭这一项阻塞小修；若继续增加职责，应拆分或说明理由。
- **历史债务**：未触及的旧代码不追溯整改，也不能成为新增同类问题的理由。

## 实施前

1. 查看 `git status --short` 和相关 diff，保护用户未提交内容。
2. 搜索可复用实现；复用会造成职责混乱时再新增能力。
3. 明确会改变的业务行为与验证方式。修改持久化、流程状态或导出时，先确定回归场景。

## 必须遵守

### 命名与文件

- 组件及组件目录使用 PascalCase；独立组件沿用 `src/components/ComponentName/index.tsx`，局部样式使用 `index.module.css`。页面使用 PascalCase；工具函数、工具文件与普通目录使用 camelCase。
- 函数和变量使用 camelCase；事件处理函数使用 `handle` 前缀；Hook 使用 `use` 前缀；模块级常量使用 UPPER_SNAKE_CASE。
- 新组件必须声明具名 Props 接口 `I[ComponentName]Props`，不得把匿名对象类型直接写在组件参数上。领域模型不为统一前缀批量改名。
- 对象形状优先使用 `interface`，联合类型使用 `type`。新增枚举采用 `[Name]Enum`，并用中文 JSDoc 说明各枚举项。

### TypeScript 与 React

- 使用函数组件和 Hooks。Props、导出函数、公共回调必须有明确类型；局部变量可推断。禁止新增 `any`，未知外部数据使用 `unknown` 并校验。
- Props 必需性应符合真实调用约束；可选值提供合理默认值。回调名要说明动作，不能只叫 `callback` 或 `handler`。
- 只有存在实际重渲染成本或稳定引用要求时才使用 `React.memo`、`useMemo`、`useCallback`。
- 不得仅为 UI 调整顺带迁移存储结构或改变流程规则。持久化、阶段流转、offer 判定、快捷增删和导出逻辑变化时，必须同步更新回归测试。

### 注释与 JSDoc

- 导出函数、组件、Hooks，以及包含业务规则或非显然边界的具名函数，必须使用中文 JSDoc 说明职责。存在独立参数时逐项写 `@param`；有非显然返回语义时写 `@returns`。Props 解构组件不机械重复接口字段。
- 阶段跳转与回退、offer 判定、流程副本、损坏数据保护、跨标签页冲突、导出转义等逻辑必须解释“为什么”和边界，不复述代码表面行为。
- 修改实现时同步更新相邻注释；过期注释视为缺陷。简单局部事件函数和一眼可见的转换无需为数量补注释。

### 导入、格式与样式

- 第三方导入在前、内部模块在后并适当分组。项目未配置路径别名，使用相对路径。
- 遵循 `vite.config.ts`：2 空格、单引号、分号、100 字符目标行宽。只格式化本次代码，不格式化业务数据。
- 新独立组件优先 CSS Modules。静态样式写入样式文件；只有依赖运行时数值或动画库的样式才保留内联。
- 新增 `!important` 必须有具体层叠原因并在附近说明。选择器保持明确作用域，通常不超过 3 层嵌套。

## 重构信号

以下情况说明文件正在承担过多职责：

- 文件超过约 500 行且本次继续加入新的状态、业务规则或大段 JSX；
- 同一行为在两个位置重复实现；
- 组件同时负责持久化、领域计算和多个独立界面区域；
- 大段静态内联样式使结构难以阅读或无法复用；
- 修改一个行为必须跨越多个不相关区域。

优先按职责提取组件、Hook、领域函数或样式模块。若只是低风险小修，拆分会显著扩大范围，可以不拆，但交付时说明信号和理由。禁止通过压缩换行规避行数问题。

## 交付前自检

- 新组件是否有具名 Props 接口和职责 JSDoc；新增导出/业务函数是否有准确类型与必要 JSDoc；
- 是否新增 `any`、匿名组件 Props、无理由的 `!important`、可移出的静态内联样式或重复逻辑；
- 是否触发重构信号，以及已拆分或暂不拆分的原因；
- 是否误改业务数据或用户未提交文件；
- 已运行哪些自动检查和场景验证，哪些没有运行。

前端代码完成后运行 `pnpm check` 和受影响的测试；当前投递功能运行 `pnpm test:tracker`。`pnpm check` 已聚合格式检查、lint 和 TypeScript 类型检查，无需重复运行 `pnpm lint`。生产构建由 `.githooks/pre-commit` 在每次提交前统一执行，日常实现完成时不重复运行；若本轮不会提交，仅在发布、部署或明确要求完整验证时手动运行 `pnpm build`。交互、视觉与导出改动还必须做实际验收；构建通过不能替代场景验收。
