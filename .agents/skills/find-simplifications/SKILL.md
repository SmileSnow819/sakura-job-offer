# 寻找简化机会

目标是删除、折叠或降级真实存在的维护面，而不是把“看起来复杂”当作问题。少量有调用关系和行为证据支撑的候选项，比大量猜测更有价值。

## 先理解当前设计

阅读目标项目的 `PRODUCT.md`、`AGENTS.md`、架构说明、Agent Notes、测试策略和相关调用路径。某些双实现、冗余检查或抽象可能是刻意保留的安全、兼容或产品边界；不要仅因局部相似就建议删除。

当用户需要广泛审计时，按领域分开调查：核心业务流程和状态、UI/API、存储和同步、任务与并发、配置与脚本、测试与文档。先查看生产代码中增量最大、生命周期最复杂的区域，不要在发现第一个未使用符号后停止。

## 强候选项

满足下列任一项且有证据时，才是值得推进的候选：

- 公共方法、事件、配置项、helper、包、脚本或状态没有生产消费者，只有测试或文档引用。
- 两个状态、缓存、事件或表示形式维护同一个事实，且没有独立的时序或所有权理由。
- 一个接口要求所有实现支持许多能力，但当前消费者只使用其中一小部分。
- 某个公共 API 只有一个内部调用方，抽象反而使该调用方更难理解。
- 为假设中的未来用户、平台、模式、兼容版本或扩展点保留了复杂路径，却没有当前产品 owner。
- 回滚、特殊测试、配置开关、格式或 UI 分支只保护已废弃或不可达的行为。
- 手写基础设施重复了当前运行时自带能力或维护良好的依赖，替换后能净删除实现、测试和文档，而不是移动复杂度。
- 独立模块只服务于测试、demo 或构建辅助，却增加发布、依赖或配置成本。

小的局部清理不必上升为设计提案；记录为简短 TODO 即可。没有消费者证据的“这看上去复杂”不是候选项。

## 调查方法

1. 从精确符号、事件名、配置键、文件格式或 API 字符串开始搜索；随后阅读所有命中，而不是只数引用数。
2. 区分生产调用、测试、文档、生成产物和示例。示例、脚本和配置可能是实际入口，不能草率归为非生产代码。
3. 追溯动态装配、反射、序列化、插件注册、环境变量和 wire format；静态未使用分析只能提供线索。
4. 对每个候选写出当前行为、生产消费者、测试/文档消费者、删除后行为和受影响的公开承诺。
5. 遇到异步代码时画出所有权和状态转换：每个 sentinel、ready promise、取消路径、disposer 和状态位必须对应唯一职责。多个机制共同表示同一“存活”或“已完成”事实时，考虑合并为一个生命周期控制器。

## 信任与依赖

审查 defensive copy、freeze、运行时校验和 callback capture 时，先问值来自哪里、下一步谁拥有它。解析器、配置加载、队列、磁盘、网络、worker 和进程边界通常需要校验或复制；同一进程内已有类型保证的调用不应无故加防御层。

建议引入依赖前，确认：运行时版本可用、依赖健康、现有代码的确切覆盖面、残余 glue code，以及净删除量。新增依赖但保留原有复杂 wrapper 并不算简化。

## 决定与输出

拒绝或降级候选，如果它会删除仍在使用的产品能力、违背已记录且仍成立的设计理由、只会制造无关 churn，或没有真正减少公开表面。

对于值得实施的跨模块简化，创建或更新 Agent Note，写明问题、消费者证据、提案、失去的能力、替代方案、风险和可观察的验收条件。对同一主题先检查已有 Note，能合并就不要新增重复记录。

报告每项候选的证据、最小安全改法、风险、需要同步删除或更新的测试/文档/配置，以及明确排除的范围。
