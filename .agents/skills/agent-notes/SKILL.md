# 管理 Agent Notes

Agent Note 是项目的决策记忆，不是任务日志、PR 描述、changelog、实现草稿或代码/API 文档的替代品。目标是减少未来 AI 和维护者重复猜测“为什么这样设计”，同时不把历史噪音永久留在活跃上下文中。

## 先确认需要写 Note

只在以下情况创建或更新：

- 选择了代码表面无法解释的架构边界、数据所有权、安全规则、兼容策略或产品限制。
- 拒绝了未来很可能再次被提出的合理方案。
- 改动跨越多个模块，且后续维护需要知道取舍、失去的能力或重审条件。
- 已有 Note 被新实现完整或部分取代。

不要为局部重命名、明显 bug 修复、单次任务记录、尚未证实的抱怨或代码已经完整表达的实现细节新增 Note。小而明确的局部清理使用 TODO / FIXME / XXX 即可。

## 建立事实与检查重叠

先阅读项目 `AGENTS.md`、`.agents/notes/README.md`、相关代码、配置、测试、文档和现有 Note。搜索同一机制、决定、被拒绝方案、API 名称和关键词。

新增 Note 时必须判断旧 Note：

- **独立有效**：保留，两者可交叉链接。
- **部分取代**：保留旧 Note，明确仍有效的部分和新 owner。
- **完全取代**：把仍有价值的理由、替代方案、限制、重审条件和验证证据迁入新 owner，再归档或删除旧 Note。

不要因为标题相似就合并；也不要因为 Note 很旧或很短就归档。判断依据是它未来能否指导真实决策。

## 生命周期

- `proposed/`：仍在讨论的方案。不要归档；若不再值得做，诚实地标记为 rejected 并说明原因。
- `implemented/`：已落地且仍对未来有指导价值的决定。保留那些解释边界、负向保证、所有权、安全、数据格式、兼容性或重新引入条件的 Note。
- `rejected/`：仅保留仍能防止未来犯同样错误的被拒绝方案；若已过时或不再诱人，删除并修复入站链接。
- `archived/`（若项目采用）：用于已完成、但未来指导价值很低的实现记录。归档内容应冻结；当前行为必须由活跃代码和文档拥有。

不要为了达到数量或字数目标归档。对相似 Note 用同一判断原则，并记录真正边界的选择。

## 写作结构

根据项目约定调整，通常应回答：

```md
# Agent Note: <行动导向的标题>

Status: proposed | implemented | rejected

## 决定或提案

现在采用、提议或拒绝什么。

## 问题与约束

当前代码、用户需求或维护成本中的具体事实。

## 替代方案与取舍

为什么合理的其他选择不适合；我们失去了什么。

## 验证与重审条件

如何证明行为成立；什么条件变化后应重新讨论。
```

使用当前时态，链接可在当前仓库解析的文件或 issue。避免 PR / review 叙述、会议实录和“这次改动”的过程语言。

## 完成前检查

- 事实是否能由当前代码、测试、文档或明确的产品选择支持？
- 是否已经检查并处理同主题的活跃 Note？
- Note 是否保留了未来决策需要的理由，而不是已删除实现的细节？
- 入站链接是否仍然有效？
- 与 Note 相关的代码、测试和文档是否已经在同一改动中更新？

最后报告新增、更新、保留、归档或删除的 Note，以及任何未决的边界判断。
