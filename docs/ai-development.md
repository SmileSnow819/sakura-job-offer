# 平时怎样用 AI 开发这个项目

这份指南给维护者看：你负责目标、取舍和验收，AI 负责理解现有代码、拆解、实现与验证。没有必要一次写完所有细节，也不需要记住每个 Skill 的名字。

## 第一次使用与新对话

在这个项目目录中开始任务，让 AI 从 [AGENTS.md](../AGENTS.md) 读取入口，再看 [项目背景与协作偏好](ai/project-context.md)。Codex 的项目指令发现机制会读取适用的 `AGENTS.md`；普通 Markdown 不会仅因存在就自动变成记忆，所以入口明确链接了必读背景。[官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

可以直接这样说：

```text
先读 AGENTS.md 和它链接的项目背景，检查当前 Git 状态。
这次要做：……
先简短说明你理解的范围和准备怎么验证；暂时不要提交或推送。
```

如果只想了解项目，把最后一句换成“只做阅读和解释，不修改文件”。如果已经有批准的方案，给出它的路径，避免 AI 从头重新讨论。

启动环境与命令见 [README](../README.md#开发与代码规范)。使用项目内的 Vite+，不需要为了启动项目另外安装全局 `vp`。

## 需求怎么说最省事

一句话目标加下面几项就够了，暂时不清楚的部分让 AI 提问：

- **目标**：谁要做什么，解决什么不便。
- **范围**：这次做什么，明确不做什么。
- **参考**：截图、页面位置、已有交互；说明希望保留和不喜欢的部分。
- **验收**：实际操作后应该出现什么结果。

例如：

```text
投递列表展开后，用户要能点击横向时间轴修改阶段。
保持现有布局，只改这部分，不加深色模式。
跳到二面时说明前面阶段如何处理，回退保留备注。
验收：能修改、刷新后保留、保存失败有提示，勾选记录不误触展开。
先讨论交互，确认后再实现。
```

这比“完善一下交互”更容易验收，也不需要指定每一行代码怎么写。

## 一次开发如何完成

1. **看现场**：AI 读相关文件、Git 状态和约束，说明已经存在什么，不从空项目的假设出发。
2. **确认范围**：对齐方案和验收；有视觉不确定性时先看一个关键画面。你确认“按这个做”后进入实施。
3. **小步实现**：一次处理一个可独立验收的部分；修 bug 先复现和定位原因，适合自动测试的逻辑先补失败用例。
4. **验证**：运行对应检查，实际操作受影响的页面或查看导出文件，并报告未测部分。
5. **审查差异**：确认需求没有遗漏、没混进无关重构或数据、没有用忽略规则掩盖问题。
6. **按需提交**：你明确要求后再按功能提交；推送与部署另行确认范围。

“实现好了”不等于“验收好了”。尤其是海报：生成 PNG 证明导出能运行，不能证明字体、布局与信息密度已经符合你的要求。

## Superpowers 在这里怎么用

项目已放入 Superpowers 的需求讨论、计划、测试、排错、审查和完成前验证 Skills。它们是工作说明，不是新模型，也不是可以替代实际测试的强制安全系统。Skills 按描述匹配或显式请求加载，不需要每轮读完整套。[Skill 机制](https://learn.chatgpt.com/docs/build-skills)

本项目从 [using-superpowers](../.agents/skills/superpowers/using-superpowers/SKILL.md) 进入。上游固定版本见 [来源记录](../.agents/superpowers-source.json)；本地 Skill 安装不等于已安装插件商店版本，也不会自动获得多代理权限或 Git hooks。

| 任务               | 一般怎样推进                                             |
| ------------------ | -------------------------------------------------------- |
| 新功能或方案不清晰 | 先讨论；小范围方案在聊天里确认，复杂功能再保存设计和计划 |
| 修 bug             | 复现、定位根因、最小修复、回归验证，不连着猜几个补丁     |
| 已批准方案的实施   | 按方案执行，实质性范围变化再确认，不重复问已经批准的内容 |
| 只看代码或分析问题 | 只读，给证据和风险，不自行实施                           |
| 文案或文档小改     | 说明范围并按当前任务授权执行，验证与改动风险相称         |

当前上游 brainstorming 包含实施前确认步骤，所以有时 AI 会先给方案并等待，不代表文件已经改了。想简化某次明确的小任务，可以直接指定：

```text
这次只是把按钮文案 A 改成 B，范围已经确认。
跳过额外的需求讨论和计划文档，直接修改、检查，不提交。
```

复杂功能的设计和计划可按对应 Skill 保存到 `docs/superpowers/specs/`、`docs/superpowers/plans/`；这是约定位置，不表示目录里已经有完成的方案。不要为每次小改生成全套文档。

如果多代理工具不可用，就在当前任务分步执行，并说明不能进行独立代理审查；不要把“创建新聊天”当成同一回事。无需为了使用 Skills 擅自修改个人 Codex 配置。

## 常用提问模板

### 改 UI

```text
参考这张截图修改……
喜欢的是……，不要的是……，保留现有……
先给关键区域预览，确认后再扩展到其他状态。
请检查窄屏、空状态、长文本和键盘焦点，不动存储逻辑。
```

### 修 bug

```text
复现步骤：……
预期结果：……
实际结果：……
请先复现并定位根因，再修复并补回归验证。
如果无法复现，说明缺什么证据，不凭猜测重写模块。
```

若只想诊断，明确说“只分析，不修复”。

### 做一次审查

```text
只审查本次 diff，不修改文件。
优先检查功能回归、数据丢失、导出安全和交互遗漏。
每项给出位置、影响、触发条件；没有证据的问题不要凑数。
```

### 拆分提交

```text
检查未提交改动，按功能拆成独立 commit。
只包含这次……相关文件，其他数据和未完成任务不要混入。
使用中文主题，不 push；提交后列出每笔内容和仍未提交的文件。
```

## 验收时看什么

| 改动             | 至少检查                                                                |
| ---------------- | ----------------------------------------------------------------------- |
| 纯文档           | 格式、相对链接、命令与配置是否一致、是否写入了未经确认的承诺            |
| 前端代码或工具链 | `pnpm check`、`pnpm test:tracker`、`pnpm build`，根据影响补场景测试     |
| 页面交互与样式   | 正常与空状态、窄屏、长文本、焦点和键盘；相关浏览器操作实际通过          |
| 状态与存储       | 跳转、回退、刷新保留、损坏数据、保存失败；保护真实记录                  |
| 导出             | 实际文件能打开、多页不截断、隐私选项生效、特殊字符安全、视觉可读        |
| 公司数据维护     | 官网来源、URL 去重、JSON 有效、构建；不把页面关键词命中当成最终人工确认 |

AI 交付时应分别说明“改了什么 / 本轮验证 / 未完成或未验证 / 是否提交推送”。旧对话里测试通过，不能证明新改动也通过。

仓库的 [Pages 工作流](../.github/workflows/deploy.yml) 目前由推送 `main` 触发，包含检查、测试、构建和部署；并未独立配置 `pull_request` 检查。不要把“本地通过”说成“远端 CI 通过”，也不要以为失败的代码一定在提交前被拦截。

提交消息按 [commit-msg 脚本](../.githooks/commit-msg) 的规则组织，例如 `docs(协作): 补充 AI 开发指南`。本地是否启用 hook 需检查 `git config --get core.hooksPath`；文档不自动启用它，也不要求每个贡献者改变全局 Git 配置。

## 切换新对话时如何交接

短任务结束后不必额外建交接文件。需要跨对话继续时，让 AI 生成下面的摘要，贴到下一对话；需要长期保留时，另存为 `docs/handoffs/日期-主题.md`。只记录必要信息，不写密钥、私人投递备注或聊天全文。

```text
任务和时间：
当前目标：
已经确认的范围与不做的部分：
工作目录、分支或 worktree：
相关设计/计划路径：
已经落地的改动及文件：
未完成的部分与阻塞：
本轮验证命令、结果与未测场景：
已产生的 commit（没有就写没有）：
必须保留的无关未提交改动：
下一步建议：
是否允许继续实施、提交、推送：分别说明。
```

下一对话可直接说：

```text
先读 AGENTS.md 和这份交接记录，再核对 Git 与相关代码。
不要重新实现已完成部分；说明你核对到的状态，再继续……
交接里的“下一步建议”不自动授权其他操作，本次只允许……
```

项目文件能携带上下文，但不会让 AI 自动知道其他聊天内容、浏览器本地数据或尚未保存的决定。若入口看起来未生效，检查是否在正确项目中开始任务，并让 AI 列出实际读取的指令文件；必要时重新开始会话。[指令排查说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md#verify-your-setup)

## 文档如何持续维护

- 项目入口只保留导航、启动步骤和边界；长期协作偏好放 [项目背景](ai/project-context.md)。
- 需求取舍与进度留在各自设计、计划和交接里，不向所有未来任务注入过期待办。
- 偏好变化时说明适用范围，不能把某次“不要深色模式”扩展成所有产品的永久规则。
- Superpowers 上游文件保持原样，项目适配写在入口与背景里；升级时记录来源并检查行为变化，避免重复安装产生冲突。
- 安装新的流程工具前，先确认它填补什么缺口。本项目使用 Superpowers；OpenSpec、Spec Kit 只是讨论过的选择，并未因此自动接入。
